\begin{abstract}
Biologists annotate genomes by searching their proteins against reference databases such as Pfam, which publish a
new release every few weeks to months. Each release forces a full re\nobreakdash-search, although most of the database has not
changed: 86.6\% of Pfam's entries were identical between releases 38.1 and 38.2.
% source: MEASURED pipeline/results/reference_kill_r1.json unchanged_strict=26082 z_new=30134; HAS 38.1; HAS 38.2; DERIVED identical_pct=100*unchanged_strict/z_new
Reusing the old results is hard, because the search programs are fixed binaries whose printed statistics depend on
the size of the whole database. We present \sys (Tool Annotation Reuse, Exact), a wrapper that reruns an unmodified
program only on the entries that can matter, with the program's own database\nobreakdash-size setting pinned to the new
release, so that the program itself prints the numbers a full run would print. \sys then tests the replay by adding
back entries it left out, and refuses, returning an ordinary full run, if any line changes. When it ships, every
output line except comment headers is byte\nobreakdash-identical to a full rerun; the assumption that makes this
possible is tested on every update, not proved.

On Pfam updates, \sys is $4.24\times$ faster than a full rerun (median of nine genomes on a dedicated server, 95\%
CI 4.17--4.68).
% source: MEASURED pipeline/results/exact_replay/headline_carc.json headline_median=4.243202948728078 bootstrap_ci95.low=4.172363531540619 bootstrap_ci95.high=4.683831507831228 n_speedups=9; NOMINAL ci=95
Across 715{,}704 output lines from HMMER and Infernal, not one differed from a full run. \sys refused DIAMOND,
whose first filter reads bytes of the neighboring database entry, and BLAST+, whose duplicate output rows our parser
cannot yet key.
% source: MEASURED pipeline/results/exact_replay/exactness_totals.json total_lines=715704 p_up=4.185705269055262e-06
\end{abstract}

\section{Introduction}
\label{sec:intro}

When a laboratory sequences a genome, it obtains thousands of protein sequences with no labels. To learn what
each protein does, researchers compare it against \textit{reference databases}: curated collections of known
protein families, such as Pfam~\cite{pfam2025}, UniProt~\cite{uniprot2025}, and InterPro~\cite{paysanlafosse2023interpro}.
A program such as HMMER~\cite{eddy2011hmmer} scores every protein against every family and reports the good
matches, called \textit{hits}. This step, called \textit{annotation}, underlies much of modern biology, from
comparative genomics to the sequence alignments used by structure predictors such as AlphaFold~\cite{jumper2021alphafold}.

Reference databases keep improving. UniProt and InterPro publish a new version, called a \textit{release},
roughly every eight weeks~\cite{uniprot2025,paysanlafosse2023interpro}, and Pfam published eight releases
between May 2024 and June 2026~\cite{pfam382relnotes}. Each release adds and revises families, so annotations
computed against an old release go out of date. The annotation programs keep no memory of earlier runs,
so the only way to update is to compare every protein against the entire new database again. Most of that
work recomputes answers that did not change: between Pfam 38.1 and 38.2, 86.6\% of the 30{,}134 families were
byte\nobreakdash-for\nobreakdash-byte identical (\cref{fig:churn}). At scale this repeated cost shapes practice. NCBI re\nobreakdash-annotates its
RefSeq collection on a rolling schedule because redoing all of it at once ``requires securing at once a
significant amount of computing resources''~\cite{li2021refseq}, and JGI states that at over 65 billion genes
``it is impossible to upgrade all genome and metagenome annotations to the latest version''~\cite{chen2021img}.

\textbf{Why reuse is hard.} It might seem easy to search only the new and edited families and keep the old results
for the rest. It is not, for three reasons. First, the results are \textit{coupled}: the statistic HMMER prints for
each hit, its E-value, is scaled by the total number of families in the database, much as a grade curved to class
size changes for every student when new students enroll. Adding families therefore changes the printed numbers of
hits on families that did not change. Rerunning HMMER on exactly the right families, without accounting for this,
changes 9{,}083 of 9{,}094 output lines for one bacterial genome.
% source: MEASURED pipeline/results/exact_replay/e1scale.json proteomes.0.Rn.vs_stock.tbl.differing_positions=9083 proteomes.0.Rn.vs_stock.tbl.lines_stock=9094
Second, the programs are unmodified binaries
maintained by others; we cannot change their code. Third, an approximately correct answer is not good enough:
pipelines that track provenance must reproduce a full run exactly, because ``pipeline differences can lead to
annotation discrepancies''~\cite{chen2021img}.

Existing tools fall short in two ways. General\nobreakdash-purpose caches, such as build systems and workflow
managers~\cite{curtsinger2022riker,xie2026incr,shiptoski2023processcache,ditommaso2017nextflow,molder2021snakemake},
remember whole commands keyed by the bytes they read. A new release changes the database file, so they rerun the
search in full. Specialized incremental search tools such as iBLAST and iSeqSearch~\cite{dash2021iblast,yoo2025iseqsearch}
are written by hand for one program and adjust the printed numbers after the fact. Their output is approximate, and
they cannot tell when their adjustment is wrong: in our experiment, only 1.3\% of the rows that iSeqSearch shared
with a full run were byte\nobreakdash-identical, and it reported 133 hits to sequences that the new release had deleted.
% source: MEASURED pipeline/results/reference_diamond/dx.json dx_i.idiamond.shared_byte_identical=407 dx_i.idiamond.shared_rows=31377 dx_i.idiamond.row_extra=133; DERIVED ident_pct=100*shared_byte_identical/shared_rows
\textit{How can we reuse earlier annotations across a database release, without modifying the programs, and either
return exactly what a full rerun would print or knowingly fall back to one?}

\begin{plainbox}{The key idea in plain terms}
In the programs we studied, entries in the database influence each other's printed results through only a few
global numbers, chiefly the database size, and the programs already accept those numbers as settings. If we tell
the program the new release's size up front (\textit{pin} it), it scores each family on its own merits. Then we can
rerun it on a small subset of the database and it prints exactly what a full run would print, digit for digit,
because the program, not our wrapper, computes every number. This is what \textit{taring} a scale does: fix the
baseline first, then weigh only what is new. When a program breaks this pattern, we try to detect it and fall back to a
full run.
\end{plainbox}

Pinning a global size is not new in itself. Parallel search tools split a database across machines and fix the
database size so that every piece prints consistent E-values~\cite{darling2003mpiblast}, and HMMER's \texttt{-Z} option
exists partly for that purpose~\cite{eddy2011hmmer}. What is missing is a way to use it across releases, for a binary we
do not control, without trusting that the binary has no other coupling. \sys supplies that: it finds which entries
changed (\cref{sec:model}), reruns each protein only against its few candidate families with the size pinned
(\cref{sec:replay}), and before returning anything adds back entries it left out and refuses if any line changes
(\cref{sec:check}). Every refusal falls back to an ordinary full run, so users always receive the program's own output.

We evaluate \sys on four programs: two where it reproduces full runs exactly (HMMER and Infernal) and two it refuses:
DIAMOND, whose results depend on database order, and BLAST+, whose output our parser cannot yet key. On Infernal, updates ran about twice as fast as a full rerun; on genomes made of
a few long DNA sequences, \sys skips two of its sampled checks and relies on the remaining two (\cref{sec:eval-time}).
Our contributions are:
\begin{enumerate}
  \item \textbf{Exact replay across releases with check\nobreakdash-or\nobreakdash-refuse.} Release\nobreakdash-diff discovery and candidate\nobreakdash-only, batched,
  pinned replay that makes an unmodified program print byte\nobreakdash-identical output, guarded by a
  probe\nobreakdash-based gate and a check, either of which refuses whenever the replay could differ (\cref{sec:design}).
  \item \textbf{A root cause for a refusal.} Investigating a failure of our first check revealed why DIAMOND cannot be
  replayed exactly: its first filter reads bytes belonging to the neighboring database entry, so its results depend
  on database order (\cref{sec:eval-safety}).
  \item \textbf{A pre\nobreakdash-registered evaluation.} Exactness over 715{,}704 output lines, speedups with their run\nobreakdash-to-run
  variation, known\nobreakdash-bad controls that must refuse, and comparisons with general\nobreakdash-purpose caches and approximate
  incremental search, from experiments whose design and pass/fail
% source: MEASURED pipeline/results/exact_replay/exactness_totals.json total_lines=715704 p_up=4.185705269055262e-06
  rules were committed before they ran (\cref{sec:eval}).
\end{enumerate}

\subsection{How Annotation Works}

An annotation program takes two inputs: a set of \textit{records}, such as the thousands of proteins of a bacterial
genome, and a \textit{reference} of \textit{entries}, such as Pfam's 30{,}134 protein families (\cref{tab:glossary}).
% source: MEASURED pipeline/results/reference_kill_r1.json z_new=30134
Each Pfam family is stored as a statistical profile, a profile hidden Markov model, that summarizes what members
of that family look like. HMMER's \texttt{hmmscan} compares every protein with every family, computes a score, and
writes one line per reported hit, containing the names of the protein and family, the score, and an E-value. The
E-value estimates how many equally good matches would occur by chance in a database of this size, and HMMER computes
it as a probability multiplied by $Z$, the number of families in the database~\cite{eddy2011hmmer}. With Pfam's curated
per\nobreakdash-family score thresholds (the \cutga option), whether a hit is reported depends only on its score against that
family's threshold~\cite{pfam2025}.

then uses the subset's size as $Z$: on one genome, such a rerun differed from a full run on 9{,}083 of 9{,}094 lines,
and the other 11 lines matched. Multiplying the cached E-values by

\section{Problem Model}
\label{sec:model}

The effect of a release travels along a chain: a release changes some entries, and changed entries change some
output lines. The goal is to produce every line of the new full run while running the program on as little as
possible. We make this precise.

\begin{definition}[Release]
A reference $R$ is a list of entries in file order. Each entry has a name and a \textit{strict hash} $h(e)$ of the
content that affects scoring. A new release $R'$ splits into \textit{stable} entries
$S = \{e \in R' : h(e) \in h(R)\}$ and \textit{changed} entries $\Delta = R' \setminus S$.
\end{definition}

\begin{definition}[Exact re\nobreakdash-annotation]
Let $f(Q,R)$ be the program's output on records $Q$ and reference $R$, and $\mathrm{body}(\cdot)$ the output with
comment lines removed. Given $f(Q,R)$ and $R'$, an exact re\nobreakdash-annotation returns $O$ with
$\mathrm{body}(O) = \mathrm{body}(f(Q,R'))$ byte for byte, or refuses and returns a full run $f(Q,R')$.
\end{definition}

\begin{definition}[Coupling]
A program is \textit{coupled} across entries if the line for record $q$ and entry $e$ can depend on entries other
than $e$. We distinguish four forms: a \textit{normalizer}, a global number computed from the whole reference, such as
$Z$; a \textit{side file}, an extra input file that lists entry names; an \textit{entry group}, a set of entries whose
hits compete, such as Rfam's clans; and \textit{neighbor coupling}, where the program reads bytes of the entries
next to $e$ in the file.
\end{definition}

\begin{definition}[Entry locality under a pin]
A program is \textit{entry-local under pin $\pi$} if, for every record $q$ and every subset $U \subseteq R'$ that
contains all entries reported for $q$ in the full run, running it on $(\{q\},U)$ with its normalizers set to $\pi(R')$
prints exactly $q$'s lines from the full run.
\end{definition}

Entry locality is what makes exact replay possible. It is a property of the program and its options, not something
\sys proves; \sys tests it before and during every replay and refuses when a test fails. We assume the program is
deterministic for fixed options and thread count, and that every input it reads is named on its command line.
\sys treats the program as a black box at run time and never reads its source code. We, the authors, did read the
source code of HMMER, Infernal, and DIAMOND, to design experiments and to explain their outcomes; none of that knowledge
is built into \sys.

\subsection{Stage 1: Entry Diff}

\sys splits both releases into entries and computes a \textit{strict hash} of each: SHA-256 over the entry's full
text, including its name, accession, description, length, Pfam's curated thresholds (GA, TC, NC), and every model line,
after dropping only lines tagged DATE (build date), BM and SM (the commands that built and calibrated the model), or COM
(comments). A renamed or re\nobreakdash-thresholded family therefore counts as changed. Entries of the new release whose hash appears in the old one are stable; all
others are changed. A cache keyed on the whole database file would miss on every entry after a release; a cache keyed
on entry hashes keeps every stable entry, 86.6\% of Pfam for 38.1$\rightarrow$38.2.
% source: MEASURED pipeline/results/reference_kill_r1.json unchanged_strict=26082 z_new=30134; HAS 38.1; HAS 38.2; DERIVED identical_pct=100*unchanged_strict/z_new; NOMINAL sha=256

\subsection{Stage 2: Contract Inference}
\label{sec:contract}

\sys must learn how the program's output depends on the reference without reading the program's code. It runs the
program on a sample of records three times: against the whole reference, and against each half of it. It then lines
up the output lines of the three runs by record and entry name.

\textit{Does the output split cleanly?} If every line of the whole run appears in exactly one half\nobreakdash-run, the output
\textit{decomposes} over entries: each line comes from one entry. If the whole run reports a line that neither half
reports, entries interact in ways \sys cannot replay, and it refuses. The opposite case, a half reporting a line the
whole omits, happens when entries compete and suppress each other; \sys accepts it only when the user declares which
entries compete (\cref{sec:gate}).

\textit{How does each number depend on the reference?} For each numeric column, \sys tests a small fixed set of
hypotheses: the column does not depend on the reference at all (\textit{identity}), or it scales with the number of
entries, their total length, or the number of hits per record. A hypothesis fits if rescaling every half\nobreakdash-run value by
the corresponding ratio reproduces the whole\nobreakdash-run value within the printed precision. A column that fits no hypothesis
causes refusal. Columns that are ranks or labels rather than measurements are recognized and left to the program to
reprint.

The result, called a \textit{contract}, records how the output splits and how each column depends on the reference.
It is computed once per command and reused for every later release.

\subsection{Stage 3: The Coupling Gate}
\label{sec:gate}

The gate turns the contract into a decision. Users may add declarations, which are data, never program names.

\textit{Size dependence $\rightarrow$ pin.} If a column scales with the reference size, \sys needs a program option that
sets that size. Users declare it (\texttt{-{}-pin~'-Z~\{entry\_count\}'}), and every experiment in this paper used a
declared pin. \sys can also search for one, by reading the program's help text and trying each numeric option until one
moves the column by exactly the predicted ratio; we tried this search only on HMMER and DIAMOND, and we have not
evaluated its risks, such as an option like a random seed moving a column by coincidence. With the option set to the
new release's value, the program prints on a subset the numbers it would print on the whole.

\textit{No size dependence $\rightarrow$ no pin.} If every column fits identity, \sys replays without a pin. This is the
case for Infernal under Rfam's recommended command, which derives its search size from the query sequence instead.

\textit{Side files and competing entries.} Rfam's recommended command passes a ``clan'' file listing families that
compete. On a subset, \sys rewrites that file to the families present, because the program rejects names it cannot
find. If any member of a declared group changes, \sys re\nobreakdash-searches the whole group, because a change to one member
can reveal a hit of another that the cache never recorded.

The gate applies three rules in order and stops at the first that fires:
\begin{equation}
D = \left\{\begin{array}{@{}lll@{}}
\dec{refuse} & \text{no contract} & \text{(R1)}\\
\dec{refuse\_pin} & \text{size-dependent, no pin} & \text{(R2)}\\
\dec{refuse\_pin} & \text{in-situ check fails} & \text{(R3)}\\
\dec{authorize} & \text{otherwise} &
\end{array}\right.
\label{eq:gate}
\end{equation}
R1 fires when the output does not split or a column fits no hypothesis. R2 fires when a column depends on the database
size and no pin is available; \sys never guesses. R3 replays the probe sample against its own hits with the pin set and
requires every byte to match the whole run. Every refusal runs the program in full; \dec{refuse\_pin} differs from
\dec{refuse} only in what it reports: the output does decompose, so declaring a working pin could enable replay.

\subsection{Stage 4: Discovery}

Changed entries may produce hits the cache has never seen. \sys runs the program on all records against the changed
entries $\Delta$ alone, with the pin set. A record's \textit{candidates} are its cached hits on stable entries plus its
new hits:
\begin{equation}
C_q = \{e \in S : (q,e) \in f(Q,R)\} \;\cup\; \{e : (q,e) \in f_\pi(Q,\Delta)\}.
\label{eq:cand}
\end{equation}
Discovery compares every record with every changed entry, so its cost is proportional to the changed fraction of the
reference. It is the one cost \sys cannot avoid (\cref{sec:cost}).

\subsection{Stage 5: Batched Exact Replay}
\label{sec:replay}

Cached lines cannot be returned as they are, because their numbers were computed for the old release. \sys instead
reruns the program on the candidates with the pin set, and the program prints the new numbers itself. Rerunning every
protein against all candidates of all proteins would waste work: on one genome, the proteins' candidates together
cover 3{,}719 families, but the mean protein has two.
% source: MEASURED pipeline/results/exact_replay/costpass_baseline.json 'replay_38.2'.runs.0.replay_entries=3719 'replay_38.2'.runs.0.candidate_pairs=9094 'replay_38.2'.runs.0.replay_records=4555; DERIVED mean_hits=candidate_pairs/replay_records
\sys therefore groups proteins into batches, runs each batch
against only its own proteins' candidates, and stitches the outputs back together in the original order. It chooses
the grouping that minimizes
\begin{equation}
T_{\text{replay}} = \alpha k + \beta \sum_b |U_b| + \gamma \sum_b |B_b|\,|U_b|,
\label{eq:batch}
\end{equation}
where $k$ is the number of batches, $|B_b|$ and $|U_b|$ the proteins and families in batch $b$, $\alpha$ the cost of
starting the program, $\beta$ the cost per family of preparing a sub\nobreakdash-database, and $\gamma$ the cost of one
protein--family comparison. Stitching is safe for HMMER because, in its source code, each protein's output block
depends only on that protein's own hits, including the column widths and the per\nobreakdash-protein statistics. As a tripwire, if
a replay ever reports a protein--family pair outside the candidates, \sys refuses (R4), because a full run could
contain pairs the cache never saw.

\subsection{Stage 6: Check or Refuse}
\label{sec:check}

The replay assumes the program is entry\nobreakdash-local. The check tries to prove that assumption wrong on the actual run. It
reruns the replay with \textit{pads}, families that were deliberately left out, added back to the subset. If the
program is entry\nobreakdash-local, pads change nothing: no candidate line changes and no pad family is reported. If anything
changes, the replay depended on what it left out, and \sys refuses (R5).

\sys uses two kinds of pads. The \textit{neighbor pad} adds, for every replayed protein, the families that sit next to
its candidates in the database file; it catches neighbor coupling by construction, the failure we found in DIAMOND
(\cref{sec:eval-safety}). \textit{Random pads} add three random samples of left\nobreakdash-out families, each as large as the
candidate set, for a fixed sample of $s=50$ proteins.
% source: MEASURED pipeline/docs/EXACT_REPLAY_PROTOCOL.md; TEXT sample_s=50
They test for dependencies of unknown form. If an unknown
dependency affects $k$ of $n$ proteins and a random pad includes the responsible family with probability $q$, the check
misses it with probability approximately
\begin{equation}
P_{\text{miss}} \approx h + (1-h)(1-q)^3, \qquad h = \binom{n-k}{s}\Big/\binom{n}{s},
\label{eq:miss}
\end{equation}
% source: MEASURED pipeline/results/reference_diamond/dx3.json; LEN pad_seeds=3; NOMINAL one=1
where $h$ is the chance that the protein sample contains no affected protein. The approximation treats each pad as a
single detection event; when several affected proteins fall in the sample, each pad has more chances to detect, so the
true miss probability is lower. The neighbor pad needs no such formula: it contains every candidate's file\nobreakdash-order
neighbor by construction. The check is a test, not a proof. As a final safeguard, an audit reruns the stock program on a
random sample of proteins, each included with probability 0.02 and at least 20 in total, and refuses if any line
differs (R6).
% source: MEASURED pipeline/docs/EXACT_REPLAY_PROTOCOL.md; TEXT audit_p=0.02; TEXT audit_floor=20

\subsection{Cost Model}
\label{sec:cost}

Let $T_{\text{stock}}$ be the time of a full run on the new release and $f_\Delta = |\Delta|/|R'|$ the fraction of entries
that changed. \sys's update time is approximately
\begin{equation}
T_{\sys} \approx a f_\Delta T_{\text{stock}} + c\, T_{\text{stock}},
\label{eq:cost}
\end{equation}
where the first term is discovery ($a$ is near one if the program's time grows linearly with database size) and $c$
collects every other cost (replay, check, audit, parsing) as a fraction of a stock run. The speedup
$1/(a f_\Delta + c)$ can never exceed $1/f_\Delta$, and even for a tiny release it cannot exceed $1/c$. The first run
also fills the cache, which costs a full run plus the contract probes; with fill time $F$ and update time $U$, \sys
becomes cheaper than repeated full runs after $n \ge (F - T_{\text{stock}})/(T_{\text{stock}} - U)$ releases.
% source: NOMINAL one=1

\section{Implementation}
\label{sec:impl}

\sys's core is 12{,}555 lines of Python, with 358 test functions. Its core contains no program names: small parsers read
% source: MEASURED pipeline/results/code_census.json acts_python_lines=12555 test_functions=358
profile databases, covariance\nobreakdash-model databases, FASTA files, and tabular outputs, and users declare pins, side files,
groups, and reporting thresholds as data. The cache is a SQLite file keyed by entry hash and record. A typical
invocation wraps the normal command shown below. The cache is namespaced by a hash of the command line with the
reference path removed, so changing any option, including the thread count, starts a new cache and a new contract.
This is conservative: repeated stock runs were byte\nobreakdash-identical in every timed experiment. The
namespace also includes a SHA-256 of the program binary, so upgrading a program in place starts a new cache.
\begin{lstlisting}
tare run --strategy reference --pin '-Z {entry_count}' \
  --cache cache.sqlite -- hmmscan --cut_ga --noali --cpu 4 \
  --tblout {output:tblout} --domtblout {output:domtblout} \
  {reference} {input}
\end{lstlisting}

\section{Evaluation}
\label{sec:eval}

We ask four questions. \textbf{Q1:} Is \sys's output identical to a full run? \textbf{Q2:} How much faster is an
update, and does the cost model predict it? \textbf{Q3:} Does \sys refuse when replay would be wrong? \textbf{Q4:} How
does it compare with existing tools?

\textbf{Method.} Every experiment followed the same protocol, designed so that a failure means the method failed rather
than that the test was blind. We first read the program's source for behaviors that could make a comparison fail for
unrelated reasons, then ran a pilot on separate data, then committed the design and pass/fail rules to version control
before the measured run. Each test included a case that must pass and a case that must fail, and a minimum number of
output lines below which a result counts as inconclusive. Measured runs used genomes drawn by a fixed random seed and
never used before. One rule changed after its pre\nobreakdash-registration, during a measured run; we disclosed the change and
reran every control (\cref{sec:eval-safety}).

\textbf{Setup.} HMMER 3.4 (\texttt{hmmscan}) with Pfam 38.1 and 38.2; Infernal 1.1.5 (\texttt{cmscan}) with Rfam 15.0
and 15.1; DIAMOND 2.2.5 and BLAST+ 2.14.1 with Swiss\nobreakdash-Prot 2026\_01 and 2026\_03; queries are bacterial genomes from NCBI
RefSeq. Server timings use a dedicated AMD EPYC 7542 node; laptop timings use an Apple laptop shared with other work and
are indicative only.

\subsection{Metrics}
\label{sec:metrics}

\textbf{Exactness.} A run is \dec{exact} if its body lines equal the stock run's as byte sequences; otherwise we count
and classify the differing lines. Over $N$ compared lines with none differing, the one\nobreakdash-sided 95\% Clopper--Pearson upper
bound on the per\nobreakdash-line error rate is
\begin{equation}
p_{\text{up}} = 1 - 0.05^{1/N}.
\label{eq:cp}
\end{equation}
% source: NOMINAL ci=95; NOMINAL alpha=0.05; NOMINAL one=1
Lines of one run share a pin and a reference, so they are not independent and the bound is descriptive, not a guarantee.
\textbf{Speedup.} For genome $g$ with $r$ alternating runs per arm, $S_g$ is the median stock wall time divided by the
median \sys wall time, both measured around the whole process. Across genomes we report the median of $S_g$ with a 95\%
percentile bootstrap interval, the geometric mean, and the range. Appendix~\ref{app:stats} defines the remaining statistics
(Wilson intervals, $t$-intervals for baseline overheads, coefficient of variation, model error, and safety outcomes).
% source: NOMINAL ci=95

\textbf{A failure, and what it revealed.} The check's design came from a failure. When we declared DIAMOND's database\nobreakdash-size
option (\texttt{-{}-dbsize}) as a pin, the replay on 300 proteins lost 6 of 31{,}377 stock lines while every other line
was byte\nobreakdash-identical, and our first check, which used only random pads, passed it. Under our pre\nobreakdash-registered rule, that was
an \dec{unsafe} result and invalidated that check. To find the cause, we added left\nobreakdash-out entries back in halves until each
missing line returned. Every one of the six lines was restored by exactly one entry: the candidate's neighbor in the
database file. \Cref{fig:diamond} shows the mechanism in DIAMOND's source: its first filter reads bytes across the
boundary into the preceding entry. DIAMOND's results therefore depend on the order of the database. A random pad contains one particular neighbor with probability 0.049, so three random pads miss it
86\% of the time, which is why the first check passed.

\section{Discussion}
\label{sec:discussion}

\textbf{Threats to validity.} \textit{Generality:} the two programs \sys replays exactly, HMMER and Infernal, come from one
research group and share code, so they may share the property that makes replay work; the two refused programs come from
other groups. We therefore claim that the method works for programs whose coupling lies in settings they expose, and that
it detects when coupling lies elsewhere; we do not claim it works for most search programs. BLAST's size pin reproduces a whole\nobreakdash-database table and the shipped gate still refuses it, so BLAST is not a second shipped program, and an exactly replayed program from an unrelated codebase remains open. \textit{Release choice:} \cref{fig:pairs} measures seven consecutive Pfam pairs. The fraction that must be rerun ranges from 2.0\% (37.3$\rightarrow$37.4) to 93.1\% (37.4$\rightarrow$38.0). We have timed only 38.1$\rightarrow$38.2, where that fraction is 13.4\%. \textit{Timing:} laptop numbers are indicative runs on a shared machine; the headline is measured on a dedicated
node with alternating runs. \textit{Check strength:} random pads miss hidden coupling, and on that grid most trials shipped a wrong replay (\cref{sec:eval-safety}).
% source: MEASURED pipeline/results/release_chain/pairs.json pairs.3.f_delta=0.020132600258732213 pairs.4.f_delta=0.9311802701115678 pairs.6.f_delta=0.13446605163602576; HAS 37.3; HAS 37.4; HAS 38.0; HAS 38.1; HAS 38.2; DERIVED small=100*pairs_3_f_delta; DERIVED big=100*pairs_4_f_delta; DERIVED timed=100*pairs_6_f_delta

\textbf{Anticipated objections.} \textit{``An expert could write this in a few lines of shell: run the changed families
with \texttt{-Z}, then rerun each protein's candidates.''} For HMMER with \cutga, yes, and that script is \sys without its
gate, check, and audit. Removing those stages from the measured laptop runs bounds what it would gain: the check and audit
took 7.6\% of a stock run, so the script would reach about $4.6\times$ where \sys reached $3.4\times$ (an estimate from the
measured stages, not a separate run). What the script cannot do is notice when its assumptions fail: run on DIAMOND, the
same script silently drops hits, which is the case \sys refuses. \textit{``Why not just rescale the cached E-values?''}
Rescaling reproduces the program's arithmetic but not its rounding, and it must be written for each program and column;
pinning lets the program print its own numbers.

\textit{``InterProScan already reuses precomputed results.''} Its lookup is keyed by the protein sequence for

\textbf{Deployment.} The natural deployment is InterProScan~\cite{jones2014interproscan} after a member\nobreakdash-database update.
Member databases that score each model against its own threshold, as Pfam does, should behave like our HMMER results;
those that compare hits across models would need declared groups or would be refused. Pfam's own pipeline,
\texttt{pfam\_scan.pl}, adds clan competition after \texttt{hmmscan}; we evaluated clan competition only for Infernal, so
that step is not covered by our HMMER results.

\textbf{General\nobreakdash-purpose incremental execution.} Build systems and workflow managers avoid repeated work by keying a command
on the bytes it reads (\cref{tab:prior}). Riker traces system calls to rerun only commands whose inputs
changed~\cite{curtsinger2022riker}; ProcessCache caches process executions~\cite{shiptoski2023processcache}; INCR memoizes
shell command effects and can split inputs into annotated chunks~\cite{xie2026incr}; Nextflow, Snakemake, and Cromwell hash
task inputs~\cite{ditommaso2017nextflow,molder2021snakemake,cromwell-call-cache}; and Mokhov et al.\ model the design
space~\cite{mokhov2018buildsystems}. Their unit of reuse is the command, so they cannot reuse part of an output whose
numbers depend on the whole database. \sys is complementary: it decides what to rerun inside one command.

\textbf{Incremental sequence search.} iBLAST searches only appended sequences and corrects BLAST's E-values with a formula
derived for BLAST~\cite{dash2021iblast}. iSeqSearch applies that correction to other programs with BLAST\nobreakdash-style output,
including DIAMOND~\cite{yoo2025iseqsearch}. GeStore runs unmodified BLAST and HMMER through administrator\nobreakdash-written plugins
that rewrite inputs and merge outputs~\cite{pedersen2014gestore}. MMseqs2 supports incremental
clustering~\cite{steinegger2017mmseqs2}. mpiBLAST splits a database across machines and fixes the global database
size so that every piece prints the E-values of a whole\nobreakdash-database search~\cite{darling2003mpiblast}; \sys borrows that
pinning and contributes what surrounds it: deciding which entries to rerun after a release, rerunning each record only on
its candidates, and refusing when a check finds coupling the pin does not cover. InterProScan and eggNOG\nobreakdash-mapper reuse precomputed matches keyed by protein
sequence~\cite{jones2014interproscan,cantalapiedra2021eggnog}. These approaches are hand\nobreakdash-built for one program, approximate
when the database changes, or keyed by query rather than database. Our DIAMOND result applies directly to them: no
correction of DIAMOND's printed numbers can recover hits its filter dropped because a neighboring entry was absent.

\textbf{Black-box decomposition and incremental computation.} KumQuat synthesizes combiners that let an unmodified command
run on pieces of its input stream~\cite{shen2022kumquat}; PaSh classifies shell commands by how they parallelize and
supplies aggregators for their outputs~\cite{vasilakis2021pash}; and Caruca classifies opaque commands by whether they keep
state~\cite{lamprou2025caruca}. Incremental view maintenance and self\nobreakdash-adjusting computation keep results current under
input changes but require the computation to be written in their framework~\cite{blakeley1986views,acar2003selective}.
These methods split an input stream or a known program; \sys splits a database argument whose size enters every printed
number, for a binary it cannot inspect. Its partition probes borrow the spirit of metamorphic
testing~\cite{chen1998metamorphic,segura2016survey} rather than claiming a new testing method.

\section{Conclusion}
\label{sec:conclusion}

Reference databases change every few weeks to months, and the programs that search them start from scratch every time. We
showed that for programs whose cross\nobreakdash-entry coupling lies in settings they already expose, this is unnecessary: pinning
those settings lets an unmodified program reprint, byte for byte, the output of a full run while searching only what
changed, and a check that adds back left\nobreakdash-out entries catches coupling the pin does not cover, as it did for DIAMOND,
whose filter reads neighboring entries. The same check misses most couplings that are not file\nobreakdash-order neighbors. Every replayed line across HMMER and Infernal in \cref{tab:exact} was identical to a full rerun. Across seven Pfam releases the fraction that must be rerun ranges from 2.0\% to 93.1\%; we have timed the 13.4\% pair, and that update ran $4.24\times$ faster than a full rerun on a dedicated server (median of nine genomes). An Infernal update ran about twice as fast with a reduced check. The next steps are timing the other releases in \cref{fig:pairs}, an unrelated program that ships, a check that bounds hidden coupling, a cheaper cache fill for Infernal, and a deployment inside InterProScan.

\section{Statistical Definitions}
\label{app:stats}

``Mean'' is the arithmetic mean $\bar x = \frac{1}{n}\sum_i x_i$; ``median'' is the sample median; the sample standard
deviation $s$ uses $n-1$ in its denominator; and ``geometric mean'' is $\big(\prod_{i=1}^{G} x_i\big)^{1/G}$, used only to
summarize ratios. Differing lines are classified as whitespace\nobreakdash-only, value\nobreakdash-only, missing, extra, or reordered.

\textbf{Wall time.} $T$ is the elapsed wall\nobreakdash-clock time of one complete invocation, measured with a monotonic clock around
the process, including start\nobreakdash-up, parsing, and all program calls. Database preparation (\texttt{hmmpress}) before either arm
is excluded from both.

\textbf{Speedup.} $S_g = \operatorname{median}_{i \le r} T^{\text{stock}}_{g,i} \big/ \operatorname{median}_{i \le r}
T^{\sys}_{g,i}$, a ratio of medians, which is robust to a single slow run. On the laptop $r=1$ for HMMER and $r=3$ for
Infernal; on the server $r=3$.
% source: NOMINAL r_ws=1; MEASURED pipeline/docs/EXACT_REPLAY_PROTOCOL.md; TEXT repeats=3
The pre\nobreakdash-registered server draw is $G=10$ genomes and 10{,}000 bootstrap resamples. Run\nobreakdash-to-run variability per arm is the
coefficient of variation $\mathrm{CV} = s/\bar T$.
% source: MEASURED pipeline/docs/EXACT_REPLAY_PROTOCOL.md; TEXT G=10; TEXT resamples=10000

\textbf{Pin necessity.} For the unpinned control, the fraction of differing lines $d = D/N$ is reported with a 95\% Wilson
score interval.
% source: NOMINAL ci=95

\textbf{Overhead of other tools.} Each paired run $j$ gives $\rho_j = T^{\text{tool}}_j / T^{\text{stock}}_j$; we report
$\bar\rho$ and the 95\% $t$-interval $\bar\rho \pm t_{0.975,\,n-1}\, s/\sqrt{n}$.
% source: NOMINAL ci=95; NOMINAL tcrit=0.975; NOMINAL one=1

\textbf{Prediction error.} For a predicted value $\hat x$ and a measured value $x$, $\varepsilon = |\hat x - x|/x$; the text
names the quantity (a stage time for discovery, a speedup for the headline and for Infernal, as pre\nobreakdash-registered); we report
the maximum over genomes.

\textbf{Agreement of approximate output.} For a tool that is not exact, we report the fraction of shared lines that are
byte\nobreakdash-identical (with a Wilson interval) and the agreement of its E-values with stock over shared lines, using
Pearson's $r$ and Kendall's tie\nobreakdash-corrected rank correlation $\tau_b$.

\textbf{Safety outcomes.} Each safety run is \dec{exact} (replay equals stock and every check passed), \dec{safe-refuse}
(a check failed and \sys ran the program in full; \textit{true} if the replay differed from stock, \textit{needless} if it
did not), or \dec{unsafe} (replay differed and every check passed). Any \dec{unsafe} result was pre\nobreakdash-registered as a
failure of the safety claim.
